# Open questions of the port

Points where the specification is ambiguous, or where it and the React Native code disagree, or where Dart forces a choice. Each one says the file, what, which choice was made and why. The choices are provisional until the question is answered. The "Decisions for you" list below names the ones where a real decision is needed; the sections after it are the whole record.

Rule applied (see [../porting.md](../porting.md)): when the specification is ambiguous, follow the React Native code (it conforms to the specification) and record the point here; when the specification and the code disagree, implement the specification and record the disagreement.

## Decisions for you

The points where the answer changes the code or the other app. The rest of the file is for reference.

1. **Unions of errors as `typedef ... = AppError`** (section "Dart conventions", `lib/domain/errors/`): Dart has no union types, so a use case no longer tells the compiler which errors it can return. Alternative: one sealed wrapper class per use case.
2. **`withVoteRecorded` on an unknown resolution** (section "Ambiguities"): the specification says "unchanged", the React Native code returns an equal new object. The Dart code follows React Native.
3. **Lower-casing of the email** (section "Ambiguities"): Dart and JavaScript differ on 467 code points, so the same unusual address can give two identities. Accept, or restrict to ASCII in both apps.
4. **`trimText` and U+0085** (section "Ambiguities"): the domain trims like JavaScript, not like Dart. Accept, or follow Dart in both.
5. **Contract scenarios that cannot be written on immutable values** (section "Contracts", `docs/parity/exceptions.md`): 6 are listed as exceptions (5 assign fields that have no setter, 1 compares identities), and the others only assert that a change of a list is refused. Accept, or keep them behind an option flag.

## Applied without question

The specification allows these (it says that a Flutter implementation follows the conventions of its language for identifiers, that Brand types are text made by their factory, that `MeetingSummary` is flattened into the meeting, and that a number that is not whole is `notAnInteger`), or the choice is forced by Dart. They are listed so that nothing is silent.

- `lib/domain/value_objects/duration.dart`: the specification's type `Duration` is `DurationMillis` in Dart, because `Duration` is a type of `dart:core` and importing both would make every use ambiguous or silently pick one. The factory keeps its name, `durationFromMillis`. If the spec name must be kept, the file would have to be imported with a prefix everywhere.
- `lib/domain/value_objects/vote_choice.dart`: the member `VOTE_CHOICE.For` is `VoteChoice.forChoice`, because `for` is a reserved word of Dart. The stable string is still `'for'`.
- `lib/domain/shared/validation.dart` (`requireIntegerInRange`, and the factories built on it): the specification types these parameters `Int`, but also says a fraction, `NaN` and an infinite value are `notAnInteger`, which an `Int` cannot be. Followed the React Native code (`number`): the Dart parameter is a `num`, and the result is an `int`.
- `lib/domain/errors/app_error.dart`: the eight families of errors are `part` files of one library (`part of 'app_error.dart'`), because Dart only lets a sealed class be extended inside its own library, and sealing is what makes a `switch` over an error exhaustive. The file mapping of the React Native code is kept (one file per family), but a file of the project imports `app_error.dart`, not `repository_error.dart`.
- `lib/domain/entities/meeting.dart`: `Meeting extends MeetingSummary` in TypeScript. In Dart `Meeting` repeats the four fields of the summary and `implements MeetingSummary`, so it can be used where a summary is expected, but a `Meeting` is never `==` to a `MeetingSummary` with the same four fields (TypeScript's `toEqual` compares the shape only). `MeetingSummary` is declared `@Freezed(copyWith: false)` because both classes would otherwise declare a `copyWith` of their own type, which cannot be combined. Nothing in the domain needs `copyWith` on a summary.

## Ambiguities (the React Native code was followed)

- `lib/domain/shared/validation.dart` (`trimText`, used by every trimmed text, the blank check of identifiers and the email): the specification says "trimmed" without saying which characters. Followed `String.prototype.trim` of JavaScript (the white space and line terminators of ECMAScript), not `String.trim` of Dart, which also removes U+0085 (a control character that JavaScript keeps). The difference shows only on an input that contains U+0085. Covered by a Dart-only test (`docs/parity/extras.md`).
- `lib/domain/value_objects/email_address.dart`: the specification says "lower-cased" without saying how. Followed `toLowerCase()`, as the React Native code does. Dart (SDK 3.13.3) and JavaScript (Node 24.18.1) follow different versions of Unicode, so they differ on 467 code points, checked by lower-casing every code point in both: `İ` (U+0130) becomes `i` in Dart and `i` + U+0307 in JavaScript; a capital sigma at the end of a word becomes `σ` in Dart and `ς` in JavaScript; and about 460 letters that the Dart tables do not know yet are left unchanged in Dart and lower-cased in JavaScript (the Cherokee letters from U+13A0, the Georgian U+10C7 and U+10CD, `Ϳ` U+037F, `Ԥ` U+0524, `Ԯ` U+052E...). The same address typed with one of them gives a different `EmailAddress` (and so a different identity sent to `auth.signIn`) in Flutter and in React Native. Not replicated: no mailbox of the demo uses these letters. A Dart-only test (`docs/parity/extras.md`) pins the letters a mailbox can have: ASCII, Latin, Greek without a final sigma, Cyrillic. Alternatives: refuse non-ASCII addresses in both apps, or write the lower-casing by hand with the same table in both languages. The question is yours.
- `lib/domain/entities/meeting.dart` (`withVoteRecorded`): the specification says the meeting "is returned unchanged" when the vote is for another meeting or for a resolution the meeting does not have. The React Native code returns the very same object for another meeting, but a new, equal object for an unknown resolution (its test says "returns an equal meeting"). Followed the React Native code, and both Dart tests keep their React Native assertions (`same` for the other meeting, `equals` for the unknown resolution). If the specification means the same object in both cases, the Dart function can return `meeting` when no item matched.

## Dart conventions that change a name or a type

- `lib/domain/errors/` (the unions of errors): TypeScript writes the errors of an operation as a union (`GetMeetingError = SessionRequiredError | SessionChangedError | RepositoryError`); Dart has no union types. The domain families are sealed classes (`RepositoryError`, `GatewayError`, `BiometricError`, `RejectionReason`...), and the unions that the application defines are a `typedef` to the closest sealed type that contains every member (often `AppError`), with the members listed in its comment. A test still compares the exact error. A reader of a result can no longer rely on the compiler to know that a given operation cannot fail with, say, `notFound`. Alternative if this is not acceptable: one sealed wrapper class per use case, which the domain errors cannot implement (the application depends on the domain, not the reverse), so each use case would wrap its errors in a second hierarchy.
- `lib/domain/value_objects/watermark.dart`: `createWatermark(reader, viewedAt)` takes any object with a `fullName` and an `email` in TypeScript (structural typing). In Dart the parameter is the interface `WatermarkReader`, which `User` implements; `test/domain/value_objects/watermark_test.dart` reads `aUser()` like the React Native one.
- `lib/domain/shared/constants.dart`: an `as const` object of strings is a Dart `enum` that implements `StableValue` (the string is `.value`). `valuesOf` returns the strings of an enumeration and `findConstant` returns the member (TypeScript returns the string, which is also the member).
- `lib/domain/entities/` (`AgendaItemInput.position`, `DocumentInput.pageCount`, `restorePendingVote(attempts:)`): the numbers that a factory validates are `num` in the input, while the entity keeps an `int` (the rule of `docs/porting.md`, section 2), because the tests (and the specification) pass `1.5` and expect `notAnInteger`.
- `lib/domain/entities/outbox_vote.dart`: the union `OutboxVote = PendingVote | RejectedVote` is a sealed freezed union (`const factory pending(...) = PendingVote`, `const factory rejected(...) = RejectedVote`). `status` is a getter that derives `OutboxStatus` from the class, not a stored field, so a rejected vote with the status `pending` cannot exist. The React Native test `leaves the pending vote untouched` checks `not.toHaveProperty('reason')`; in Dart a `PendingVote` has no `reason` at all, so the test checks `isNot(isA<RejectedVote>())` and that the vote is unchanged.
- `lib/domain/entities/meeting.dart` (`createMeeting`): `List.sort` of Dart is not stable, `Array.prototype.sort` is. It makes no difference here: two agenda items with the same position are refused just before, so the sort never has a tie to break.
- `lib/domain/entities/vote.dart`: the `Brand<string, 'IdempotencyKey'>` is the extension type `IdempotencyKey`. The test that feeds `idempotencyKeyOf` a lone surrogate casts a `String` (`'\uD800' as ResolutionId`), as the TypeScript test casts it, because the parsers refuse such an id.
- `test/domain/literals_test.dart`: the `as const` objects are compared with `toEqual({ For: 'for', ... })`, keys included. The Dart enums compare `{member name: stable string}` (`forChoice`, not `For`), so the member names are pinned as well as the strings.
- `lib/domain/entities/` (inputs): an input with more than three fields is a small `final class` (`AgendaItemInput`, `DocumentInput`, `ResolutionInput`, `MeetingSummaryInput`, `MeetingInput`, `VoteInput`, `AppLockInput`, `VotingEligibilityInput`), as `docs/porting.md` says; with up to three fields they are named parameters (`createUser`, `createParticipant`, `createSession`, `restorePendingVote`). The React Native tests spread a shared `VALID` object (`{ ...VALID, title: '' }`); the Dart tests use a small `_valid({...})` helper with the overridable fields instead.

## Tooling

- `pubspec.yaml`, the README and the CI: the command is `dart run build_runner build`, without `--delete-conflicting-outputs`. `build_runner` 2.16 removed that flag (it is ignored with a warning) and overwrites conflicting outputs by default.
- `.github/workflows/ci.yml` (job "Scenario parity with React Native"): reads the React Native test sources statically, and the Dart names with `dart test --reporter json`. Run against the React Native repository at the commit of `docs/parity/RN_COMMIT`, it expands every `it.each` and contract suite to the 1105 names that `jest --json` reports (checked locally: 1105 exact, 0 missing, 0 extra). A table that the reader cannot compute (a call of a function other than a one-`return` function) becomes a wildcard in the name and matches by pattern; none is left today. `--rn-names <jest json>` compares against the names Jest itself reports instead.

## Ports and fakes (`lib/application/ports`, `test/application/support`)

- `lib/application/ports/*.dart` (`SignInFailure`, `VoteSubmissionError`): the unions of errors that a port declares have no Dart equivalent, so they are `typedef`s to `AppError`, with the members in the comment (the rule of `docs/porting.md`, section 5). `SignInFailure` is `invalidCredentials`, `networkUnavailable`, `unexpected` or `storageWriteFailed`; `VoteSubmissionError` is a `GatewayError` or a `VotingError`. The ports that return one family keep it (`Result<Page<MeetingSummary>, GatewayError>`, `Result<Meeting, RepositoryError>`, `Result<void, StorageWriteFailedError>`).
- `lib/application/ports/monitoring.dart` (`LogAttributes`): `{ readonly [Key in LogAttribute]?: string | number | boolean }` is `Map<LogAttribute, Object>`. Dart has no union of `String`, `num` and `bool`; the type does not say which values are allowed (the comment does). A sealed wrapper type would be the alternative, at the cost of every call site writing `LogValue.text(...)`. The optional `attributes` parameter of `log` and `captureError` is an optional positional parameter.
- `lib/application/ports/vote_outbox.dart` (`EnqueueResult`): the TypeScript union of three object shapes is a sealed freezed union (`Enqueued`, `AlreadyQueued(existing:)`, `HeldByUnreadable`), the same pattern as `OutboxVote`. `outcome` is a getter that gives the `EnqueueOutcome` of the class, as `status` is for `OutboxVote`. A test compares with `equals(ok(const EnqueueResult.enqueued()))` where the React Native one compares with `{ outcome: ENQUEUE_OUTCOME.Enqueued }`.
- `lib/application/ports/*.dart` (`BIOMETRIC_REASON`, `CONNECTIVITY_STATUS`, `SCREEN_CAPTURE_KIND`, `ENQUEUE_OUTCOME`, `LOG_LEVEL`, `MONITORING_EVENT`, `LOG_ATTRIBUTE`): kept in the file of the port that owns them, like the React Native files, and written as enums (`docs/porting.md`, section 4). The 33 events, the 17 attributes and the 2 levels are the ones of the specification, in its order (checked against the React Native object and the tables of `docs/spec/ports.md`: same names, same strings).
- `test/application/support/copy_plain.dart` (`copyPlain`): the React Native function deep-copies plain objects so that a test cannot pass because a use case mutated a value the fake also holds. Dart has no such risk: the entities, pages and errors are immutable (freezed, unmodifiable lists), so `copyPlain` returns its argument. The lists the fakes build themselves are new lists (`List.of`). One contract scenario does touch it: `meetingRepositoryContract` "is a copy: changing a meeting or a page that was returned changes nothing the next call returns" empties the arrays of what it got back (`mutableArray(...).length = 0`). The lists of a Dart meeting or page are unmodifiable, so that change cannot be written; the contracts assert that the change throws `UnsupportedError` and that the next call still answers the original (see "Contracts").
- `test/application/support/create_fakes.dart`: `createFakes()` returns the `Fakes` class (the React Native return is an object literal; `ReturnType<typeof createFakes>` is `Fakes`). `appLock`, `screenProtectionCoordinator` and the `implements` of the deps interfaces were added with the shared helpers (see "Shared helpers" below).
- `test/application/support/fake_vote_outbox.dart` (`seed`): `seed(...entries)` is variadic in TypeScript and takes a `List<OutboxVote>` in Dart. `seedUnreadable(voterId, [key])` keeps its optional key as an optional positional parameter.
- `test/application/support/fake_meeting_repository.dart` (`list`): `Array.prototype.sort` is stable and `List.sort` of Dart is not, so the fake sorts with the position in the given list as tie-break; meetings scheduled at the same instant keep the order they were given in, as in the React Native fake. A Dart-only test pins it (`docs/parity/extras.md`).
- `test/application/support/fake_clock.dart` (`FakeClock.set`): kept as a method called `set`, as in TypeScript. `FakeClock.advance(int millis)` takes an `int`, not a `num`.
- `test/application/support/fakes_test.dart`: the React Native constants (`PAGE_KEY`, `SESSION`...) are local constants or `final`s of the group; `itemsOf` returns the value or the error as an `Object`, as the TypeScript helper returns `result.ok ? result.value : result.error`. The scenario `fakes.votes.submit(aVote({ choice: VOTE_CHOICE.For }))` keeps the explicit choice and silences `avoid_redundant_argument_values` on that line, since `for` is also the default of the builder.
- `docs/porting.md`, section 2: an `enum` constructor is `new(this.value)`, not `const new(this.value)`: `const` is implied and the lint `unnecessary_const_in_enum_constructor` refuses it (the section said `const new`, which no enum of `lib/` uses).

## Shared helpers (`lib/application/shared`)

- `lib/application/shared/` (the `XxxDeps` interfaces): TypeScript passes any object that has the right properties, so `loadWithCacheFallback` hands its `deps` to `endRefusedSession`, `purgeCaches` and `requireSession` without a word. Dart is nominal, so the interfaces are a chain that adds one dependency at a time: `PurgeCachesDeps` (the two caches and the monitoring), `EndSessionDeps implements PurgeCachesDeps` (adds `auth` and `appLock`), `RequireSessionDeps implements EndSessionDeps` (adds `clock`), `CacheFallbackDeps implements RequireSessionDeps` (adds `maxCacheAge`) and `LoadMeetingDeps implements CacheFallbackDeps` (adds `meetings`). Each has exactly the properties of the React Native interface of the same name, with the inherited ones not repeated; `Fakes` implements all of them. The use cases that come next extend the interface of the helper they call (`ListMeetingsDeps implements CacheFallbackDeps`...).
- `lib/application/shared/require_session.dart` (`SessionRequiredError`, and the errors of `loadWithCacheFallback`, `loadMeeting`, `requireSameUser`): a union of errors of several families, so `typedef SessionRequiredError = AppError` and `Future<Result<Loaded<T>, AppError>>` (the rule of `docs/porting.md`, section 5). The members are listed in the comment of each function. A test compares the exact error with `equals(err(...))`.
- `lib/application/shared/load_with_cache_fallback.dart` (`CacheFallbackSource`): the TypeScript interface of five methods and two properties is a `final class` whose members are functions (`fetch`, `save`, `read`, `remove`, `revoke`), because that is how `loadMeeting` and the other callers build one (with closures). A `CacheFallbackSource<T, E extends RepositoryError>` keeps the two type parameters of the React Native one. The `resource` of the logs is put in the attributes as its stable string (`CacheResource.meeting.value`), the way the React Native attribute holds `'meeting'`; a test compares with the same string.
- `lib/application/shared/loaded.dart` (`DataSource`, `Freshness`): `FRESHNESS` is the enum `Freshness`, and the union `DataSource = { freshness: Fresh } | { freshness: Stale, cachedAt }` is a sealed freezed union (`FreshSource`, `StaleSource(cachedAt:)`), the same pattern as `OutboxVote` and `EnqueueResult`; `freshness` is a getter that gives the `Freshness` of the class, not a stored field. A test compares with `const DataSource.fresh()` and `DataSource.stale(cachedAt: ...)` where the React Native one compares with the objects.
- `lib/application/shared/app_lock.dart` (`AppLockOptions`): the options object with one property is the named parameter `AppLock({bool locked = true})`. The public constructor delegates to a private one because a private field cannot be a named parameter.
- `lib/application/shared/session_policy.dart` (`SessionEndingCode`, `isSessionEndingCode`): `code is SessionEndingCode` is a type guard that narrows a `string` to a union of literals. Dart cannot narrow a `String`, so `isSessionEndingCode` returns a `bool`, and `SessionEndingCode` is a `typedef` to `String` kept for the name (it says nothing to the compiler). `SESSION_ENDING_CODES` and `RETRYABLE_CODES` are `sessionEndingCodes` (an unmodifiable list) and `retryableCodes` (an unmodifiable set) of `String`s built from the members of the code enums (`docs/porting.md`, section 4). `SESSION_CHECK_INTERVAL_MILLIS` is `sessionCheckIntervalMillis`.
- `lib/application/shared/screen_protection_coordinator.dart` (`ScreenProtectionCoordinatorDeps`): `new ScreenProtectionCoordinator({ screenProtection })` takes an object with a property; the Dart constructor takes a `ScreenProtectionCoordinatorDeps` (an interface with the `screenProtection` getter). A test that builds a coordinator by hand uses `ScreenProtectionDeps(screenProtection)` of `test/application/support/screen_protection_deps.dart`. The queue is a `Future<void>` chain like the Promise chain of the React Native class, and, as there, a task that fails does not stop the next one; no `Result` ever carries a thrown error, so this only matters if a platform adapter throws, which the port forbids.
- `test/application/support/create_fakes.dart` (`Fakes.copyWith`, `appLock`, `screenProtectionCoordinator`): `Fakes` now carries `appLock` (unlocked) and `screenProtectionCoordinator` (over the same `FakeScreenProtection`), as `createFakes` of React Native does. The spread with an override (`{ ...fakes, appLock: new AppLock() }`, `{ ...createFakes(), maxCacheAge }`) is `fakes.copyWith(appLock: ..., maxCacheAge: ..., maxAttempts: ...)`: the other fakes are shared with the copy, as in a spread. The overrides of a port by something that is not the fake (`{ ...fakes, meetingCache: new HoldingMeetingCache(...) }`, `{ ...fakes, outbox }`) cannot be typed in `Fakes`, whose fields are the fakes themselves (the tests read `fakes.meetingCache.isEmpty()`), so a test that needs one writes a small class that implements the deps and forwards to the fakes: `_DepsWithCache` in `record_vote_in_cache_test.dart`. The use-case tests that come next do the same, or extend `copyWith`.
- `test/application/shared/load_with_cache_fallback_test.dart` (`scriptedSource`): the React Native helper takes a promise per operation (`fetch: Promise.resolve(ok(REMOTE)).then((result) => { deps.auth.session = ...; return result; })`), which runs the side effect when the test awaits. The Dart helper takes `fetch` as a function and the other operations as the `Result` they answer, so a side effect that happens "while the request is on its way" is written inside the function before it returns. It runs at the same moment of the scenario (after the remote call started, before the answer is used). The counters (`reads`, `removals`, `revocations`) are fields of the helper instead of functions.
- `test/application/shared/screen_protection_coordinator_test.dart`: `setImmediate` (the `settle` of the React Native test) is `Future.delayed(Duration.zero)`, a turn of the event loop after the microtasks; the platform calls the manual platform records are an enum (`enable`, `disable`) instead of strings.

## Use cases: auth and connectivity (`lib/application/use_cases/auth`, `connectivity`)

- `lib/application/use_cases/auth/sign_in.dart`, `sign_out.dart`, `restore_session.dart`, `get_current_user.dart` (`SignInDeps`, `SignOutDeps`, `RestoreSessionDeps`, `GetCurrentUserDeps`): the React Native interfaces list properties that are exactly those of a helper's deps (`SignInDeps` and `SignOutDeps` are the five properties of `EndSessionDeps`, `RestoreSessionDeps` and `GetCurrentUserDeps` the six of `RequireSessionDeps`), and `GetCurrentUserDeps` is already a type alias there. Dart is nominal, so each is a `typedef` to the helper's interface, which `Fakes` already implements. A new interface per use case would need `Fakes` (outside this scope) to implement it. `UnlockAppDeps`, `ObserveConnectivityDeps` and `EvaluateAppLockDeps` have properties no helper has and are `abstract interface class`es; `Fakes` implements `UnlockAppDeps` and `ObserveConnectivityDeps`, so those tests pass `fakes` directly (`ObserveConnectivity` keeps a private `_Deps` only for the tests that give a connectivity of their own). `EvaluateAppLockDeps` is not implemented by `Fakes`, because `gracePeriod` is a setting and not a fake: its test passes a small private `_Deps` class that forwards to the fakes and adds the `gracePeriod` that `{ ...fakes, gracePeriod }` adds.
- `lib/application/use_cases/auth/sign_in.dart` (`SignInInput`), `evaluate_app_lock.dart` (`EvaluateAppLockInput`): the input interfaces have two and one fields, so by the rule of `docs/porting.md` (section 6) `execute` takes named parameters, `execute(email:, password:)` and `execute(backgroundedAt:)`, and there is no `SignInInput` type.
- `lib/application/use_cases/auth/sign_in.dart` (`SignInError`): `ValidationError | SignInFailure` is a `typedef` to `AppError`, with its members in the comment (section 5). `andThenAsync` is given its type arguments (`<Credentials, Session, AppError>`) because the validation and the sign-in fail with different families.
- `lib/application/use_cases/auth/restore_session.dart` (`SESSION_RESTORE`, `RestoredSession`): `SESSION_RESTORE` is the enum `SessionRestore` (section 4); `RestoredSession`, an object literal of the single field `status`, is the record `({SessionRestore status})`, which compares by value and prints as `(status: SessionRestore.none)`, so the tests compare with `ok((status: SessionRestore.none))` as the React Native ones do with the literal. A freezed class would have added a generated file for one field. The "says nothing of who the user is" scenario searches `'$restored'` where the React Native one searches `JSON.stringify(restored)`: a record has no JSON form, and its text is all there is to leak.
- `lib/application/use_cases/connectivity/observe_connectivity.dart` (`ConnectivityObservation`): the interface of two fields is a `final class` with two final fields (no freezed: one of them is a function, so equality would mean nothing). The `latest ??= read` of the TypeScript is the same expression in Dart; `status` is read from the assignment because a local that a closure assigns is not promoted to non-null.
- `test/application/use_cases/connectivity/observe_connectivity_test.dart`: the object literals typed `Connectivity` (`noisy`, `slow`, `counting`) are instances of the private `_ScriptedConnectivity`, whose two operations are functions the test gives; `new Promise((resolve) => { answer = resolve; })` is a `Completer`. The destructuring `const { unsubscribe } = await observe()` is `observation.unsubscribe()`.
- `test/application/use_cases/auth/sign_in_test.dart` ("is locked while the caches are emptied, and opened only afterwards"): the React Native test replaces `fakes.meetingCache.purge` with a function that records the lock. Dart cannot replace a method of an instance, so the test uses a subclass of `FakeMeetingCache` (`_SpyMeetingCache`) that records the lock and calls `super.purge()`, with a deps class that carries it (the same pattern as `_DepsWithCache` of `record_vote_in_cache_test.dart`). The first scenario's expected credentials keep the explicit `anEmail('alice@example.com')` and silence `avoid_redundant_argument_values`, since that is the default of the builder.
- `test/application/use_cases/auth/restore_session_test.dart` and `sign_out_test.dart`: `expect(fakes.monitoring.logs).toEqual([{ level, event, attributes: undefined }])` is a list with a `LogRecord(..., attributes: null)`; `fakes.outbox.seed(aPendingVote())` is `seed([aPendingVote()])` and `ok(undefined)` read from the cache is `ok<void>(null)`, which compares equal to `Ok(null)`.

## Use cases: meetings and documents (`lib/application/use_cases/meetings`, `documents`)

- `lib/application/use_cases/meetings/get_meeting.dart` (`GetMeetingDeps`): the React Native alias `GetMeetingDeps = LoadMeetingDeps` is a `typedef` to `LoadMeetingDeps`, which `Fakes` already implements, so `GetMeeting(fakes)` reads as in the tests of React Native. `ListMeetingsDeps`, `OpenDocumentDeps`, `CloseDocumentDeps` and `ObserveScreenCaptureDeps` have properties no helper has and are `abstract interface class`es that `Fakes` implements, so their tests pass `fakes` directly (the forwarding class `MeetingsDocumentsDeps` of the first draft was removed).
- `lib/application/use_cases/meetings/*.dart`, `documents/*.dart` (`GetMeetingInput`, `ListMeetingsInput`, `OpenDocumentInput`, `CloseDocumentInput`, `ObserveScreenCaptureInput`): the input interfaces have one or two fields, so, as for the auth use cases and by the rule of `docs/porting.md` (section 6), `execute` takes named parameters and there is no input type. `ObserveScreenCapture.execute(input, onCapture)` becomes `execute(documentId:, onCapture:)`, both named, because a positional parameter cannot follow the named ones in the order of the TypeScript. In `list_meetings_test.dart` the constants that were `ListMeetingsInput` objects are records `({MeetingPeriod period, PageRequest request})`, which is also the type of the calls the fake repository records, so `expect(listCalls).toEqual([FIRST])` stays `equals([_first])`.
- `lib/application/use_cases/meetings/get_meeting.dart`, `list_meetings.dart`, `documents/open_document.dart` (`GetMeetingError`, `ListMeetingsError`, `OpenDocumentError`): the unions are `typedef`s to `AppError` with their members in the comment (section 5). The exact union is still checked by the tests, which compare with `equals(err(...))`. `ObserveScreenCapture` fails with `SessionRequiredError`, which is already a `typedef` to `AppError` in `require_session.dart`.
- `lib/application/use_cases/documents/open_document.dart` (`OpenedDocument`): the interface of five fields is a freezed class (value equality, needed by `equals(ok(OpenedDocument(...)))`, as `toEqual` compares the object literal in the TypeScript). ## Contracts (`test/application/support/contracts`)

- `test/application/support/contracts/*.dart` (the harnesses): a TypeScript harness is an object literal with methods, some optional (`reopen`, `failNextStatement`, `plantUnreadable`, `files`). In Dart each harness is a `final class` whose members are functions passed as named constructor parameters (`MeetingCacheHarness(cache: ..., breakWrites: ..., repairWrites: ...)`), optional ones nullable, so `fakes_contracts_test.dart` reads like the TypeScript and a real adapter builds one the same way. The options objects (`StoreContractOptions`, `DocumentCacheContractOptions`, `VoteOutboxContractOptions`...) are small classes; the spread `{ ...IN_MEMORY_STORE, keepsFiles: false }` is spelled out with the three flags (`StoreContractOptions` is a `base class` so the two others can extend it). `setOnline(online: false)` takes a named boolean (the lint `avoid_positional_boolean_parameters`).
- `test/application/support/contracts/*.dart` (`describe.skip`): `(flag ? describe : describe.skip)('name', fn)` is `group('name', fn, skip: !flag)`. The body of a skipped group still runs in `package:test`, so the tests are declared and counted, and shown as skipped, as in Jest.
- `test/application/support/contracts/*` (the no-aliasing checks, `keeps no reference to the objects that go in or out` and `is a copy`): the TypeScript tests change a value in place through a cast (`mutable(x).title = 'DEFACED'`, `mutableArray(x).length = 0`) and check that the store did not follow. The Dart values are immutable (freezed, no setter) and the lists they hold are unmodifiable, so the only change that can be attempted is on a list, and a list refuses it with `UnsupportedError`. Choice made: a scenario that has a list to change keeps its name and asserts that the change is refused (`expectRefused` in `support.dart`) and that the store still answers the original value (4 of `MeetingCache`, `MeetingRepository` "is a copy", and "after they were listed" of `VoteOutbox`); a scenario whose only changes are assignments to fields has nothing left to attempt, and is listed in `exceptions.md` (5 scenarios). The 6th, "hands out a new object at every read" (`first.value?.value === second.value?.value` must be false), could be written with `identical`, but the Dart fakes share the immutable value on purpose (checked: `identical` is true for two reads of `FakeMeetingCache`), so the scenario would fail on them for a reason that is not a defect; it is listed in `exceptions.md` for that reason. If a real adapter must be held to it, the scenario can be kept behind an option flag of the contract, like `keepsFiles`. The alternative is to keep all of them as tests that only read back what was saved, which would pass without checking anything.
- `test/application/support/contracts/meeting_cache_contract.dart`, `document_cache_contract.dart` (`deface`, assignments to `cachedAt`, `location`): the part of a scenario that assigned a field (`mutable(read.value).cachedAt = at(999)`) is dropped, since `CacheEntry` has no setter; the rest of the scenario is kept.
- `test/application/support/contracts/support.dart` (`valueOf`, `trickyIds`, `errorCodeOf`): `valueOf` throws a `StateError` with the error printed with `$error` where the TypeScript one uses `JSON.stringify`. `TRICKY_IDS` is `trickyIds`, a `const List<String>`. `errorCodeOf` is the Dart form of `!failed.ok && failed.error.code`, which in TypeScript evaluates to `false` for a success; here a success gives `null`, and the comparison with the expected code fails the same way. `mutable` and `mutableArray` have no Dart counterpart (see above).
- `test/application/support/contracts/document_cache_contract.dart` (`hexOf`): the TypeScript walks the code points and takes `charCodeAt(0)` of each; Dart walks the UTF-16 code units. They give the same name for every id of the suite, which are all in the basic plane.
- `test/application/support/contracts/meeting_repository_contract.dart` (`idsOf`): the TypeScript returns an object compared with `toEqual`; the Dart value is a record whose list does not compare deeply with `==`, so the "answers the same page to the same request" scenario compares `ids` and `nextCursor` one after the other.
- `test/application/support/fakes_contracts_test.dart` (`FakeMeetingRepository`): the TypeScript `serve` hands the fake `{ id, title, scheduledAt, location }` summaries built by destructuring the meeting. In Dart a `Meeting` implements `MeetingSummary` but is never `==` to one, so the summary is built with `aMeetingSummary(...)` from the four fields, which is what the destructuring stands for.

## Votes use cases (`lib/application/use_cases/votes`)

- `lib/application/use_cases/votes/*.dart` (`CastVoteDeps`, `SyncPendingVotesDeps`, `ListPendingVotesDeps`, `AcknowledgeRejectedVoteDeps`, `DiscardUnreadableVotesDeps`): each is an `abstract interface class` that extends the helper interface it calls (`LoadMeetingDeps` or `RequireSessionDeps`) and adds `outbox`, `votes`, `biometricGate` or `maxAttempts`. `Fakes` in `test/application/support/create_fakes.dart` implements the five, so the tests pass `fakes` directly, and `{ ...fakes, maxAttempts: 3 }` is `fakes.copyWith(maxAttempts: 3)`. Only the replacement of a port by something that is not the fake (`{ ...fakes, outbox }`, a slow biometric gate) keeps a wrapper, `VotesDeps` of `test/application/use_cases/votes/votes_support.dart`, which takes the `outbox` or the `biometricGate` to replace.
- `lib/application/use_cases/votes/*.dart` (`CastVoteOutcome`, `OutboxContent`, `RejectedSync`, `SyncReport` and its three variants): `freezed` classes, as `docs/porting.md` (section 6) says. Generated, so that `==` and `toString` follow the fields: a field added to a report is printed by `toString` without anyone writing it. That is what makes the text of a report a fair stand-in for `JSON.stringify` in the "never the choices" tests (see below).
- `lib/application/use_cases/votes/*.dart` (`CastVoteError`, `SyncInterruption`, `SyncPendingVotesError`, `ListPendingVotesError`, `AcknowledgeRejectedVoteError`, `DiscardUnreadableVotesError`): unions of errors of several families, so `typedef ... = AppError` with the members listed in the comment (`docs/porting.md`, section 5). The private `queue(vote, cause: Undelivered)` of `CastVote` takes an `AppError`: its two possible members (`networkUnavailable`, `unexpected`) have no common sealed type but `AppError`. A test compares the exact error, as in React Native.
- `lib/application/use_cases/votes/sync_pending_votes.dart` (`SyncReport`, `SyncProgress`): the TypeScript union `SyncAlreadyRunning | SyncCompleted | SyncInterrupted`, where the last two extend the interface `SyncProgress`, is a sealed freezed union (`const factory alreadyRunning() = SyncAlreadyRunning`, `completed(...) = SyncCompleted`, `interrupted(...) = SyncInterrupted`); `SyncCompleted` and `SyncInterrupted` implement the interface `SyncProgress` (`synced`, `rejected`, `remaining`) through `@Implements<SyncProgress>()`. `outcome` is a getter that gives the `SyncOutcome` of the class (the React Native object stores it as a field), as `status` is for `OutboxVote`. `SYNC_OUTCOME` and `CAST_VOTE_STATUS` are the enums `SyncOutcome` and `CastVoteStatus`, with the stable strings of the specification. The private `Settlement` union is four private final classes.
- `lib/application/use_cases/votes/cast_vote.dart` and `acknowledge_rejected_vote.dart` (`CastVoteInput`, `AcknowledgeRejectedVoteInput`): no Dart input type; `execute` takes named parameters, `execute(meetingId:, resolutionId:, choice:)` and `execute(resolutionId:)`, like every other use case (`docs/porting.md`, section 6: at most three fields). A first draft kept an input class for these two; it was removed so that the presentation of step 5 calls all the use cases in one style. - `lib/application/use_cases/votes/cast_vote.dart` and `sync_pending_votes.dart` (answers of the server): the React Native code compares the codes (`error.code === REPOSITORY_ERROR_CODE.Unexpected`) and uses the type guard `isVotingError`. - `lib/application/use_cases/votes/cast_vote.dart` (`queue`): the three cases of `enqueue` (`outcome === HeldByUnreadable`, `=== AlreadyQueued`, else enqueued) are an exhaustive `switch` over the sealed `EnqueueResult` (`HeldByUnreadable`, `AlreadyQueued(:existing)`, `Enqueued`), and the pending-or-rejected `existing` is a `switch` over `OutboxVote`.
