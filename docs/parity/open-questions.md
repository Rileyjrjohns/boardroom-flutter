# Open questions of the port

Points where the specification is ambiguous, or where it and the React Native code disagree, or where Dart forces a choice. Each one says the file, what, which choice was made and why. The "Decisions" list below gives the points where a real decision was needed and what was decided; the sections after it are the whole record.

Rule applied (see [../porting.md](../porting.md)): when the specification is ambiguous, follow the React Native code (it conforms to the specification) and record the point here; when the specification and the code disagree, implement the specification and record the disagreement.

## Decisions

The points where the answer changes the code or the other app, each with the decision taken (step 2, on 2026-10-22). The rest of the file is for reference.

1. **Unions of errors as `typedef ... = AppError`** (section "Dart conventions", `lib/core/domain/errors/`): Dart has no union types, so a use case no longer tells the compiler which errors it can return. Alternative: one sealed wrapper class per use case. **Decided: keep `AppError`**; each comment lists the members and the tests compare the exact error.
2. **`withVoteRecorded` on an unknown resolution** (section "Ambiguities"): the specification says "unchanged", the React Native code returns an equal new object. The Dart code follows React Native. **Decided: the specification was corrected** in the React Native repository (commit `3e2c909`): the same meeting for another meeting, an equal copy for an unknown resolution.
3. **Lower-casing of the email** (section "Ambiguities"): Dart and JavaScript differ on 467 code points, so the same unusual address can give two identities. Accept, or restrict to ASCII in both apps. **Decided: accept**, documented and pinned by Dart-only tests.
4. **`trimText` and U+0085** (section "Ambiguities"): the domain trims like JavaScript, not like Dart. Accept, or follow Dart in both. **Decided: accept** (the domain trims like JavaScript in both apps).
5. **Contract scenarios that cannot be written on immutable values** (section "Contracts", `docs/parity/exceptions.md`): 6 are listed as exceptions (5 assign fields that have no setter, 1 compares identities), and the others only assert that a change of a list is refused. Accept, or keep them behind an option flag. **Decided: accept the exceptions.**

## Applied without question

The specification allows these (it says that a Flutter implementation follows the conventions of its language for identifiers, that Brand types are text made by their factory, that `MeetingSummary` is flattened into the meeting, and that a number that is not whole is `notAnInteger`), or the choice is forced by Dart. They are listed so that nothing is silent.

- `lib/core/domain/value_objects/duration.dart`: the specification's type `Duration` is `DurationMillis` in Dart, because `Duration` is a type of `dart:core` and importing both would make every use ambiguous or silently pick one. The factory keeps its name, `durationFromMillis`. If the spec name must be kept, the file would have to be imported with a prefix everywhere.
- `lib/features/meetings/domain/value_objects/vote_choice.dart`: the member `VOTE_CHOICE.For` is `VoteChoice.forChoice`, because `for` is a reserved word of Dart. The stable string is still `'for'`.
- `lib/core/domain/shared/validation.dart` (`requireIntegerInRange`, and the factories built on it): the specification types these parameters `Int`, but also says a fraction, `NaN` and an infinite value are `notAnInteger`, which an `Int` cannot be. Followed the React Native code (`number`): the Dart parameter is a `num`, and the result is an `int`.
- `lib/core/domain/errors/app_error.dart`: the eight families of errors are `part` files of one library (`part of 'app_error.dart'`), because Dart only lets a sealed class be extended inside its own library, and sealing is what makes a `switch` over an error exhaustive. The file mapping of the React Native code is kept (one file per family), but a file of the project imports `app_error.dart`, not `repository_error.dart`.
- `lib/features/meetings/domain/entities/meeting.dart`: `Meeting extends MeetingSummary` in TypeScript. In Dart `Meeting` repeats the four fields of the summary and `implements MeetingSummary`, so it can be used where a summary is expected, but a `Meeting` is never `==` to a `MeetingSummary` with the same four fields (TypeScript's `toEqual` compares the shape only). `MeetingSummary` is declared `@Freezed(copyWith: false)` because both classes would otherwise declare a `copyWith` of their own type, which cannot be combined. Nothing in the domain needs `copyWith` on a summary.

## Ambiguities (the React Native code was followed)

- `lib/core/domain/shared/validation.dart` (`trimText`, used by every trimmed text, the blank check of identifiers and the email): the specification says "trimmed" without saying which characters. Followed `String.prototype.trim` of JavaScript (the white space and line terminators of ECMAScript), not `String.trim` of Dart, which also removes U+0085 (a control character that JavaScript keeps). The difference shows only on an input that contains U+0085. Covered by a Dart-only test (`docs/parity/extras.md`).
- `lib/features/auth/domain/value_objects/email_address.dart`: the specification says "lower-cased" without saying how. Followed `toLowerCase()`, as the React Native code does. Dart (SDK 3.13.3) and JavaScript (Node 24.18.1) follow different versions of Unicode, so they differ on 467 code points, checked by lower-casing every code point in both: `İ` (U+0130) becomes `i` in Dart and `i` + U+0307 in JavaScript; a capital sigma at the end of a word becomes `σ` in Dart and `ς` in JavaScript; and about 460 letters that the Dart tables do not know yet are left unchanged in Dart and lower-cased in JavaScript (the Cherokee letters from U+13A0, the Georgian U+10C7 and U+10CD, `Ϳ` U+037F, `Ԥ` U+0524, `Ԯ` U+052E...). The same address typed with one of them gives a different `EmailAddress` (and so a different identity sent to `auth.signIn`) in Flutter and in React Native. Not replicated: no mailbox of the demo uses these letters. A Dart-only test (`docs/parity/extras.md`) pins the letters a mailbox can have: ASCII, Latin, Greek without a final sigma, Cyrillic. Alternatives: refuse non-ASCII addresses in both apps, or write the lower-casing by hand with the same table in both languages. The question is yours.
- `lib/features/meetings/domain/entities/meeting.dart` (`withVoteRecorded`): the specification says the meeting "is returned unchanged" when the vote is for another meeting or for a resolution the meeting does not have. The React Native code returns the very same object for another meeting, but a new, equal object for an unknown resolution (its test says "returns an equal meeting"). Followed the React Native code, and both Dart tests keep their React Native assertions (`same` for the other meeting, `equals` for the unknown resolution). If the specification means the same object in both cases, the Dart function can return `meeting` when no item matched.

## Dart conventions that change a name or a type

- `lib/core/domain/errors/` (the unions of errors): TypeScript writes the errors of an operation as a union (`GetMeetingError = SessionRequiredError | SessionChangedError | RepositoryError`); Dart has no union types. The domain families are sealed classes (`RepositoryError`, `GatewayError`, `BiometricError`, `RejectionReason`...), and the unions that the application defines are a `typedef` to the closest sealed type that contains every member (often `AppError`), with the members listed in its comment. A test still compares the exact error. A reader of a result can no longer rely on the compiler to know that a given operation cannot fail with, say, `notFound`. Alternative if this is not acceptable: one sealed wrapper class per use case, which the domain errors cannot implement (the application depends on the domain, not the reverse), so each use case would wrap its errors in a second hierarchy.
- `lib/features/documents/domain/value_objects/watermark.dart`: `createWatermark(reader, viewedAt)` takes any object with a `fullName` and an `email` in TypeScript (structural typing). In Dart the parameter is the interface `WatermarkReader`, which `User` implements; `test/features/documents/domain/value_objects/watermark_test.dart` reads `aUser()` like the React Native one.
- `lib/core/domain/shared/constants.dart`: an `as const` object of strings is a Dart `enum` that implements `StableValue` (the string is `.value`). `valuesOf` returns the strings of an enumeration and `findConstant` returns the member (TypeScript returns the string, which is also the member).
- `lib/features/*/domain/entities/` (`AgendaItemInput.position`, `DocumentInput.pageCount`, `restorePendingVote(attempts:)`): the numbers that a factory validates are `num` in the input, while the entity keeps an `int` (the rule of `docs/porting.md`, section 2), because the tests (and the specification) pass `1.5` and expect `notAnInteger`.
- `lib/features/votes/domain/entities/outbox_vote.dart`: the union `OutboxVote = PendingVote | RejectedVote` is a sealed freezed union (`const factory pending(...) = PendingVote`, `const factory rejected(...) = RejectedVote`). `status` is a getter that derives `OutboxStatus` from the class, not a stored field, so a rejected vote with the status `pending` cannot exist. The React Native test `leaves the pending vote untouched` checks `not.toHaveProperty('reason')`; in Dart a `PendingVote` has no `reason` at all, so the test checks `isNot(isA<RejectedVote>())` and that the vote is unchanged.
- `lib/features/meetings/domain/entities/meeting.dart` (`createMeeting`): `List.sort` of Dart is not stable, `Array.prototype.sort` is. It makes no difference here: two agenda items with the same position are refused just before, so the sort never has a tie to break.
- `lib/features/votes/domain/entities/vote.dart`: the `Brand<string, 'IdempotencyKey'>` is the extension type `IdempotencyKey`. The test that feeds `idempotencyKeyOf` a lone surrogate casts a `String` (`'\uD800' as ResolutionId`), as the TypeScript test casts it, because the parsers refuse such an id.
- `test/core/domain/literals_test.dart`: the `as const` objects are compared with `toEqual({ For: 'for', ... })`, keys included. The Dart enums compare `{member name: stable string}` (`forChoice`, not `For`), so the member names are pinned as well as the strings.
- `lib/features/*/domain/entities/` (inputs): an input with more than three fields is a small `final class` (`AgendaItemInput`, `DocumentInput`, `ResolutionInput`, `MeetingSummaryInput`, `MeetingInput`, `VoteInput`, `AppLockInput`, `VotingEligibilityInput`), as `docs/porting.md` says; with up to three fields they are named parameters (`createUser`, `createParticipant`, `createSession`, `restorePendingVote`). The React Native tests spread a shared `VALID` object (`{ ...VALID, title: '' }`); the Dart tests use a small `_valid({...})` helper with the overridable fields instead.

## Tooling

- `pubspec.yaml`, the README and the CI: the command is `dart run build_runner build`, without `--delete-conflicting-outputs`. `build_runner` 2.16 removed that flag (it is ignored with a warning) and overwrites conflicting outputs by default.
- `.github/workflows/ci.yml` (job "Scenario parity with React Native"): reads the React Native test sources statically, and the Dart names with `dart test --reporter json`. Run against the React Native repository at the commit of `docs/parity/RN_COMMIT`, it expands every `it.each` and contract suite to the 1105 names that `jest --json` reports (checked locally: 1105 exact, 0 missing, 0 extra). A table that the reader cannot compute (a call of a function other than a one-`return` function) becomes a wildcard in the name and matches by pattern; none is left today. `--rn-names <jest json>` compares against the names Jest itself reports instead.

## Ports and fakes (`lib/core/application/ports`, `lib/features/*/application/ports`, `test/support/fakes`)

- `lib/{core,features/*}/application/ports/*.dart` (`SignInFailure`, `VoteSubmissionError`): the unions of errors that a port declares have no Dart equivalent, so they are `typedef`s to `AppError`, with the members in the comment (the rule of `docs/porting.md`, section 5). `SignInFailure` is `invalidCredentials`, `networkUnavailable`, `unexpected` or `storageWriteFailed`; `VoteSubmissionError` is a `GatewayError` or a `VotingError`. The ports that return one family keep it (`Result<Page<MeetingSummary>, GatewayError>`, `Result<Meeting, RepositoryError>`, `Result<void, StorageWriteFailedError>`).
- `lib/core/application/ports/monitoring.dart` (`LogAttributes`): `{ readonly [Key in LogAttribute]?: string | number | boolean }` is `Map<LogAttribute, Object>`. Dart has no union of `String`, `num` and `bool`; the type does not say which values are allowed (the comment does). A sealed wrapper type would be the alternative, at the cost of every call site writing `LogValue.text(...)`. The optional `attributes` parameter of `log` and `captureError` is an optional positional parameter.
- `lib/features/votes/application/ports/vote_outbox.dart` (`EnqueueResult`): the TypeScript union of three object shapes is a sealed freezed union (`Enqueued`, `AlreadyQueued(existing:)`, `HeldByUnreadable`), the same pattern as `OutboxVote`. `outcome` is a getter that gives the `EnqueueOutcome` of the class, as `status` is for `OutboxVote`. A test compares with `equals(ok(const EnqueueResult.enqueued()))` where the React Native one compares with `{ outcome: ENQUEUE_OUTCOME.Enqueued }`.
- `lib/{core,features/*}/application/ports/*.dart` (`BIOMETRIC_REASON`, `CONNECTIVITY_STATUS`, `SCREEN_CAPTURE_KIND`, `ENQUEUE_OUTCOME`, `LOG_LEVEL`, `MONITORING_EVENT`, `LOG_ATTRIBUTE`): kept in the file of the port that owns them, like the React Native files, and written as enums (`docs/porting.md`, section 4). The 33 events, the 17 attributes and the 2 levels are the ones of the specification, in its order (checked against the React Native object and the tables of `docs/spec/ports.md`: same names, same strings).
- `test/support/fakes/copy_plain.dart` (`copyPlain`): the React Native function deep-copies plain objects so that a test cannot pass because a use case mutated a value the fake also holds. Dart has no such risk: the entities, pages and errors are immutable (freezed, unmodifiable lists), so `copyPlain` returns its argument. The lists the fakes build themselves are new lists (`List.of`). One contract scenario does touch it: `meetingRepositoryContract` "is a copy: changing a meeting or a page that was returned changes nothing the next call returns" empties the arrays of what it got back (`mutableArray(...).length = 0`). The lists of a Dart meeting or page are unmodifiable, so that change cannot be written; the contracts assert that the change throws `UnsupportedError` and that the next call still answers the original (see "Contracts").
- `test/support/fakes/create_fakes.dart`: `createFakes()` returns the `Fakes` class (the React Native return is an object literal; `ReturnType<typeof createFakes>` is `Fakes`). `appLock`, `screenProtectionCoordinator` and the `implements` of the deps interfaces were added with the shared helpers (see "Shared helpers" below).
- `test/support/fakes/fake_vote_outbox.dart` (`seed`): `seed(...entries)` is variadic in TypeScript and takes a `List<OutboxVote>` in Dart. `seedUnreadable(voterId, [key])` keeps its optional key as an optional positional parameter.
- `test/support/fakes/fake_meeting_repository.dart` (`list`): `Array.prototype.sort` is stable and `List.sort` of Dart is not, so the fake sorts with the position in the given list as tie-break; meetings scheduled at the same instant keep the order they were given in, as in the React Native fake. A Dart-only test pins it (`docs/parity/extras.md`).
- `test/support/fakes/fake_clock.dart` (`FakeClock.set`): kept as a method called `set`, as in TypeScript. `FakeClock.advance(int millis)` takes an `int`, not a `num`.
- `test/support/fakes/fakes_test.dart`: the React Native constants (`PAGE_KEY`, `SESSION`...) are local constants or `final`s of the group; `itemsOf` returns the value or the error as an `Object`, as the TypeScript helper returns `result.ok ? result.value : result.error`. The scenario `fakes.votes.submit(aVote({ choice: VOTE_CHOICE.For }))` keeps the explicit choice and silences `avoid_redundant_argument_values` on that line, since `for` is also the default of the builder.
- `docs/porting.md`, section 2: an `enum` constructor is `new(this.value)`, not `const new(this.value)`: `const` is implied and the lint `unnecessary_const_in_enum_constructor` refuses it (the section said `const new`, which no enum of `lib/` uses).

## Shared helpers (`lib/core/application/offline`, `lib/features/auth/application/session`)

- `lib/core/application/offline/`, `lib/features/auth/application/session/` and `lib/features/meetings/application/load_meeting.dart` (the `XxxDeps` interfaces): TypeScript passes any object that has the right properties, so `loadWithCacheFallback` hands its `deps` to `endRefusedSession`, `purgeCaches` and `requireSession` without a word. Dart is nominal, so the interfaces are a chain that adds one dependency at a time: `PurgeCachesDeps` (the two caches and the monitoring), `EndSessionDeps implements PurgeCachesDeps` (adds `auth` and `appLock`), `RequireSessionDeps implements EndSessionDeps` (adds `clock`), `CacheFallbackDeps implements RequireSessionDeps` (adds `maxCacheAge`) and `LoadMeetingDeps implements CacheFallbackDeps` (adds `meetings`). Each has exactly the properties of the React Native interface of the same name, with the inherited ones not repeated; `Fakes` implements all of them. The use cases that come next extend the interface of the helper they call (`ListMeetingsDeps implements CacheFallbackDeps`...).
- `lib/features/auth/application/session/require_session.dart` (`SessionRequiredError`, and the errors of `loadWithCacheFallback`, `loadMeeting`, `requireSameUser`): a union of errors of several families, so `typedef SessionRequiredError = AppError` and `Future<Result<Loaded<T>, AppError>>` (the rule of `docs/porting.md`, section 5). The members are listed in the comment of each function. A test compares the exact error with `equals(err(...))`.
- `lib/core/application/offline/load_with_cache_fallback.dart` (`CacheFallbackSource`): the TypeScript interface of five methods and two properties is a `final class` whose members are functions (`fetch`, `save`, `read`, `remove`, `revoke`), because that is how `loadMeeting` and the other callers build one (with closures). A `CacheFallbackSource<T, E extends RepositoryError>` keeps the two type parameters of the React Native one. The `resource` of the logs is put in the attributes as its stable string (`CacheResource.meeting.value`), the way the React Native attribute holds `'meeting'`; a test compares with the same string.
- `lib/core/application/offline/loaded.dart` (`DataSource`, `Freshness`): `FRESHNESS` is the enum `Freshness`, and the union `DataSource = { freshness: Fresh } | { freshness: Stale, cachedAt }` is a sealed freezed union (`FreshSource`, `StaleSource(cachedAt:)`), the same pattern as `OutboxVote` and `EnqueueResult`; `freshness` is a getter that gives the `Freshness` of the class, not a stored field. A test compares with `const DataSource.fresh()` and `DataSource.stale(cachedAt: ...)` where the React Native one compares with the objects.
- `lib/features/auth/application/session/app_lock.dart` (`AppLockOptions`): the options object with one property is the named parameter `AppLock({bool locked = true})`. The public constructor delegates to a private one because a private field cannot be a named parameter.
- `lib/features/auth/application/session/session_policy.dart` (`SessionEndingCode`, `isSessionEndingCode`): `code is SessionEndingCode` is a type guard that narrows a `string` to a union of literals. Dart cannot narrow a `String`, so `isSessionEndingCode` returns a `bool`, and `SessionEndingCode` is a `typedef` to `String` kept for the name (it says nothing to the compiler). `SESSION_ENDING_CODES` and `RETRYABLE_CODES` are `sessionEndingCodes` (an unmodifiable list) and `retryableCodes` (an unmodifiable set) of `String`s built from the members of the code enums (`docs/porting.md`, section 4). `SESSION_CHECK_INTERVAL_MILLIS` is `sessionCheckIntervalMillis`.
- `lib/features/documents/application/screen_protection_coordinator.dart` (`ScreenProtectionCoordinatorDeps`): `new ScreenProtectionCoordinator({ screenProtection })` takes an object with a property; the Dart constructor takes a `ScreenProtectionCoordinatorDeps` (an interface with the `screenProtection` getter). A test that builds a coordinator by hand uses `ScreenProtectionDeps(screenProtection)` of `test/support/fakes/screen_protection_deps.dart`. The queue is a `Future<void>` chain like the Promise chain of the React Native class, and, as there, a task that fails does not stop the next one; no `Result` ever carries a thrown error, so this only matters if a platform adapter throws, which the port forbids.
- `test/support/fakes/create_fakes.dart` (`Fakes.copyWith`, `appLock`, `screenProtectionCoordinator`): `Fakes` now carries `appLock` (unlocked) and `screenProtectionCoordinator` (over the same `FakeScreenProtection`), as `createFakes` of React Native does. The spread with an override (`{ ...fakes, appLock: new AppLock() }`, `{ ...createFakes(), maxCacheAge }`) is `fakes.copyWith(appLock: ..., maxCacheAge: ..., maxAttempts: ...)`: the other fakes are shared with the copy, as in a spread. The overrides of a port by something that is not the fake (`{ ...fakes, meetingCache: new HoldingMeetingCache(...) }`, `{ ...fakes, outbox }`) cannot be typed in `Fakes`, whose fields are the fakes themselves (the tests read `fakes.meetingCache.isEmpty()`), so a test that needs one writes a small class that implements the deps and forwards to the fakes: `_DepsWithCache` in `record_vote_in_cache_test.dart`. The use-case tests that come next do the same, or extend `copyWith`.
- `test/core/application/offline/load_with_cache_fallback_test.dart` (`scriptedSource`): the React Native helper takes a promise per operation (`fetch: Promise.resolve(ok(REMOTE)).then((result) => { deps.auth.session = ...; return result; })`), which runs the side effect when the test awaits. The Dart helper takes `fetch` as a function and the other operations as the `Result` they answer, so a side effect that happens "while the request is on its way" is written inside the function before it returns. It runs at the same moment of the scenario (after the remote call started, before the answer is used). The counters (`reads`, `removals`, `revocations`) are fields of the helper instead of functions.
- `test/features/documents/application/screen_protection_coordinator_test.dart`: `setImmediate` (the `settle` of the React Native test) is `Future.delayed(Duration.zero)`, a turn of the event loop after the microtasks; the platform calls the manual platform records are an enum (`enable`, `disable`) instead of strings.

## Use cases: auth and connectivity (`lib/features/auth/application/use_cases`, `lib/core/application/use_cases`)

- `lib/features/auth/application/use_cases/sign_in.dart`, `sign_out.dart`, `restore_session.dart`, `get_current_user.dart` (`SignInDeps`, `SignOutDeps`, `RestoreSessionDeps`, `GetCurrentUserDeps`): the React Native interfaces list properties that are exactly those of a helper's deps (`SignInDeps` and `SignOutDeps` are the five properties of `EndSessionDeps`, `RestoreSessionDeps` and `GetCurrentUserDeps` the six of `RequireSessionDeps`), and `GetCurrentUserDeps` is already a type alias there. Dart is nominal, so each is a `typedef` to the helper's interface, which `Fakes` already implements. A new interface per use case would need `Fakes` (outside this scope) to implement it. `UnlockAppDeps`, `ObserveConnectivityDeps` and `EvaluateAppLockDeps` have properties no helper has and are `abstract interface class`es; `Fakes` implements `UnlockAppDeps` and `ObserveConnectivityDeps`, so those tests pass `fakes` directly (`ObserveConnectivity` keeps a private `_Deps` only for the tests that give a connectivity of their own). `EvaluateAppLockDeps` is not implemented by `Fakes`, because `gracePeriod` is a setting and not a fake: its test passes a small private `_Deps` class that forwards to the fakes and adds the `gracePeriod` that `{ ...fakes, gracePeriod }` adds.
- `lib/features/auth/application/use_cases/sign_in.dart` (`SignInInput`), `evaluate_app_lock.dart` (`EvaluateAppLockInput`): the input interfaces have two and one fields, so by the rule of `docs/porting.md` (section 6) `execute` takes named parameters, `execute(email:, password:)` and `execute(backgroundedAt:)`, and there is no `SignInInput` type.
- `lib/features/auth/application/use_cases/sign_in.dart` (`SignInError`): `ValidationError | SignInFailure` is a `typedef` to `AppError`, with its members in the comment (section 5). `andThenAsync` is given its type arguments (`<Credentials, Session, AppError>`) because the validation and the sign-in fail with different families.
- `lib/features/auth/application/use_cases/restore_session.dart` (`SESSION_RESTORE`, `RestoredSession`): `SESSION_RESTORE` is the enum `SessionRestore` (section 4); `RestoredSession`, an object literal of the single field `status`, is the record `({SessionRestore status})`, which compares by value and prints as `(status: SessionRestore.none)`, so the tests compare with `ok((status: SessionRestore.none))` as the React Native ones do with the literal. A freezed class would have added a generated file for one field. The "says nothing of who the user is" scenario searches `'$restored'` where the React Native one searches `JSON.stringify(restored)`: a record has no JSON form, and its text is all there is to leak.
- `lib/core/application/use_cases/observe_connectivity.dart` (`ConnectivityObservation`): the interface of two fields is a `final class` with two final fields (no freezed: one of them is a function, so equality would mean nothing). The `latest ??= read` of the TypeScript is the same expression in Dart; `status` is read from the assignment because a local that a closure assigns is not promoted to non-null.
- `test/core/application/use_cases/observe_connectivity_test.dart`: the object literals typed `Connectivity` (`noisy`, `slow`, `counting`) are instances of the private `_ScriptedConnectivity`, whose two operations are functions the test gives; `new Promise((resolve) => { answer = resolve; })` is a `Completer`. The destructuring `const { unsubscribe } = await observe()` is `observation.unsubscribe()`.
- `test/features/auth/application/use_cases/sign_in_test.dart` ("is locked while the caches are emptied, and opened only afterwards"): the React Native test replaces `fakes.meetingCache.purge` with a function that records the lock. Dart cannot replace a method of an instance, so the test uses a subclass of `FakeMeetingCache` (`_SpyMeetingCache`) that records the lock and calls `super.purge()`, with a deps class that carries it (the same pattern as `_DepsWithCache` of `record_vote_in_cache_test.dart`). The first scenario's expected credentials keep the explicit `anEmail('alice@example.com')` and silence `avoid_redundant_argument_values`, since that is the default of the builder.
- `test/features/auth/application/use_cases/restore_session_test.dart` and `sign_out_test.dart`: `expect(fakes.monitoring.logs).toEqual([{ level, event, attributes: undefined }])` is a list with a `LogRecord(..., attributes: null)`; `fakes.outbox.seed(aPendingVote())` is `seed([aPendingVote()])` and `ok(undefined)` read from the cache is `ok<void>(null)`, which compares equal to `Ok(null)`.

## Use cases: meetings and documents (`lib/features/meetings/application/use_cases`, `lib/features/documents/application/use_cases`)

- `lib/features/meetings/application/use_cases/get_meeting.dart` (`GetMeetingDeps`): the React Native alias `GetMeetingDeps = LoadMeetingDeps` is a `typedef` to `LoadMeetingDeps`, which `Fakes` already implements, so `GetMeeting(fakes)` reads as in the tests of React Native. `ListMeetingsDeps`, `OpenDocumentDeps`, `CloseDocumentDeps` and `ObserveScreenCaptureDeps` have properties no helper has and are `abstract interface class`es that `Fakes` implements, so their tests pass `fakes` directly (the forwarding class `MeetingsDocumentsDeps` of the first draft was removed).

## Infrastructure (step 3)

The foundations of the infrastructure: dependencies, shared helpers, clock, monitoring, the wire classes of the API, the loader of the fixtures, files, documents, PDF and secure storage. The adapters written by the other parts of the step add their own points here.

- `pubspec.yaml` (encrypted database): `sqlcipher_flutter_libs` is end of life (its last version, `0.7.0+eol`, says "update to version 3.x of package:sqlite3"). The project uses the build hook of `sqlite3` 3.x with `hooks.user_defines.sqlite3.source: sqlite3mc` (SQLite3MultipleCiphers), selected with `PRAGMA cipher = 'sqlcipher'` before `PRAGMA key = "x'<64 hexadecimal digits>'"`. `test/core/infrastructure/persistence/encrypted_sqlite_test.dart` opens a database file on the host with and without the key, through `sqlite3` and through `drift`: the file holds no readable text, a wrong key and no key are refused, `PRAGMA rekey` works. The format is the one SQLite3MultipleCiphers documents as SQLCipher 4; it was not compared with a file written by the SQLCipher library itself.
- `pubspec.yaml` (encrypted database, in memory): SQLite3MultipleCiphers refuses a key on a database in memory ("Setting key not supported for in-memory or temporary databases"). The unlock is therefore for files only, and the tests that run drift in memory open a plain database. React Native has no such case (its in-memory tests use a simulated opener). A test pins the refusal.
- `pubspec.yaml` (what was not run): the build hook downloads the prebuilt SQLite3MultipleCiphers for the platform of the build. It was run on the macOS host, under `dart test` and `flutter test`. The iOS and Android builds, and the Ubuntu runner of the CI, need nothing installed (no `apt` package), but were not run here: no application is launched in this step.
- `pubspec.yaml` (`fake_async`): a development dependency, for the two tests that check a timer (`timerSleep` waits the delay and not before, `attempt` leaves no timer running).
- `pubspec.yaml` (`connectivity_plus`): added for the connectivity adapter of the step (the React Native `ExpoConnectivity`); `tool/check_imports.dart` now refuses it, with `path_provider`, outside the infrastructure folders (`lib/core/infrastructure`, `lib/features/*/infrastructure`) and `lib/app`.
- `lib/core/infrastructure/http/dto/` and `lib/features/*/infrastructure/dto/` (zod to `json_serializable`): the wire classes are `@JsonSerializable(checked: true)`, so a missing field and a field of the wrong type are `CheckedFromJsonException`s with the key, and `decodeWire` turns them into a `WireFailure` with the path (`agenda.1.status`, found by walking the body down to the map that failed). Zod collects every flaw and the diagnostic lists up to ten paths; the generated code stops at the first, so the diagnostic lists that one. An item of a list that is not an object is reported at the list (`agenda`), not at the position (`agenda.0`). An optional field that is present and `null` is refused (`disallowNullValue`), as `.optional()` refuses it. `issuePathsOf` keeps the sorting, the removal of repeats and the limit of ten, over the paths it is given.
- `lib/core/infrastructure/http/dto/wire.dart` (instants): `DateTime.parse` rolls an impossible day over to the next month (`2030-02-30` is the 2nd of March), where `Date.parse` refuses it. The instants of the wire are read by a parser of their own, on the numbers: the format of the React Native schema, a month 1-12, a day of the month, hour 0-23 (24:00:00 alone, as `Date.parse` accepts it), minute and second 0-59, an offset up to 23:59, a year `-000000` refused, any fraction truncated to milliseconds, a time beyond the range of a date (8.64e15 ms) refused. They are written as `Date.prototype.toISOString` writes them (a year outside 0000-9999 with a sign and six digits). A negative instant is read (the domain refuses it afterwards, as in React Native).
- `lib/core/infrastructure/http/protocol.dart`: `HTTP_STATUS` is `HttpStatusCode` (`HttpStatus` is a class of `dart:io`) and carries the number in `code`; `ROUTES` is the class `Routes`; `encodeURIComponent` is `Uri.encodeComponent`, which leaves the same characters alone and replaces a lone surrogate where `encodeURIComponent` throws.

A device on a wifi without internet is therefore `online` for the app, and the repositories fail with `networkUnavailable` on their first request, as they do for any request that cannot reach the server. The seam that `HttpClientOptions.fetch` is in React Native is `HttpClientOptions.adapter`, a dio `HttpClientAdapter`: the development build gives it the fixture server's adapter, a test of the client gives it `test/support/infrastructure/scripted_adapter.dart` (the counterpart of the scripted `fetch`), and nothing gives the platform's own. - `lib/core/infrastructure/http/http_client.dart` (retry): the brief asks for a retry interceptor; there is none, because the React Native client retries nothing. `docs/api.md` puts the retry of a vote in the synchronisation of the outbox (and says the client does not read `Retry-After`), and a retry of a query in the presentation. A retry in the client would be a second policy beside theirs (and a vote sent several times would count as one attempt), so the client reports a failure once and the layers above decide. The only interceptor is the one that attaches the token (`_BearerAuthInterceptor`); the comment of `dio` in `pubspec.yaml` ("interceptors for the session and the retries") says more than the code does.
- `lib/core/infrastructure/http/http_client.dart` (`HttpFailure`): React Native's `HttpFailure` is a union of the repository errors and `RequestRejected`, told apart by `code`. The repository errors are a sealed family of the domain that cannot be extended elsewhere, and a rejection is not one of them, so `HttpFailure` is a sealed class with two members: `RequestFailed(error)`, which holds the `RepositoryError`, and `RequestRejected(error)`, which holds the `error` member of the body. `HTTP_FAILURE_CODE` is not ported (a test `is RequestRejected`), and `asGatewayError` and `asRepositoryError` switch over the two members.
- `lib/core/infrastructure/http/http_client.dart` (`Described`): React Native takes a request as its description or as a function that builds it. Dart has no cheap union, so `request`, `perform` and `download` take a function only (`Spec Function()`), which always runs where the client can catch a failure; a test that has a description gives `() => spec` or a tear-off.
- `lib/core/infrastructure/http/http_client.dart` (`schema`): the zod `schema` of `HttpRequestSpec` is `decode`, a function from the decoded JSON (`null` for an empty body) to a `Result<T, WireFailure>`; the repositories give `(json) => decodeWire(json, XWire.fromJson)`. The client reports its failure the way it reports a zod one: the places that broke the shape, never what they held. `WHOLE_BODY_PATH` is `rootPath` of `shared/issue_paths.dart`.
- `lib/core/infrastructure/http/http_client.dart` (time): React Native aborts an `AbortController` when a timer fires and races the request against it. The client does the same with a `CancelToken` and `Future.any`, and also gives dio the limit as its `connectTimeout` and `receiveTimeout`, so that the adapter of a device bounds a connection that hangs or goes silent whatever happens in Dart. The timer is cancelled when the request ends (a test with `fakeAsync` checks that none is left).
- `lib/core/infrastructure/http/http_client.dart` (a body nobody reads): dio subscribes to the body of an answer as soon as it has the headers and buffers it, whether or not the client reads it (`handleResponseStream`). The limit therefore holds the way React Native's does only because the client cancels the request in every case where it leaves a body behind: a body that grows past the limit, a declared length that is too large, the body of a refusal that a download does not read, and the body of a success that `perform` does not want (React Native's `perform` leaves such a body to the platform and aborts nothing). A test that checks that a body "is not read" uses a paced answer (`ScriptedAnswer.paced`), because with dio the first chunk comes with the answer unless the answer waits.
- `lib/core/infrastructure/http/http_client.dart` (platforms with no stream): `readBounded` and `readBytes` have a fallback for a `fetch` that gives no `body` (React Native's), which reads the text or the `ArrayBuffer` whole and checks its size after. dio always gives a stream, so the fallback is not ported, and four tests that exist for it are not either (one in `HttpClient.test.ts`, three in `HttpClient.download.test.ts`).
- `lib/core/infrastructure/http/http_client.dart` (`Content-Length`): the declared length is read like `Number(header)` followed by `Number.isInteger`: the text is trimmed, parsed as a number (`num.tryParse`), and kept if it is a whole number (`1048576.0` and `1e6` are, `many` is not). `Number('')` is 0 in JavaScript and `null` in Dart, which are the same for the check (0 is never over the limit).
- `lib/core/infrastructure/http/http_client.dart` (a body that is not UTF-8): `TextDecoder` and `utf8.decode(allowMalformed: true)` both replace a malformed sequence with U+FFFD. A leading byte order mark is kept by `utf8.decode` and dropped by `TextDecoder`; the body is trimmed with `trimText` (which removes U+FEFF, as `String.prototype.trim` does) before it is parsed, so the two read the same text.
- `lib/core/infrastructure/http/http_client.dart` (a token source that throws): in React Native a `BearerTokenSource.token()` that rejects would reject the request (`SessionVault` never does). The interceptor catches it and answers `unexpected` with the cause `credentials unreadable`, as it does for a `Result` that is an error, so that the client never throws whatever it is given.
- `lib/core/infrastructure/http/http_client.dart` (`close`): `HttpClient.close()` is new. dio keeps connections open, and the composition root of a later step has to let go of them when the app is torn down; a request made after it is `networkUnavailable`.
- `lib/core/infrastructure/http/well_formed.dart` (a lone surrogate): `encodeURIComponent` throws for a lone surrogate, and `Uri.encodeComponent` writes U+FFFD instead and sends something else than it was given. The adapters call `requireWellFormed` (and `encodeUriComponent`, which does) where React Native relies on the exception: an identifier, a query value or a header value that is not well formed UTF-16 makes a request that is not built (`unexpected`, `request could not be built`), and nothing is sent. `IllFormedTextException` says nothing of the text.
- `lib/core/infrastructure/http/invalid_response.dart` (constants): `HTTP_RESOURCE`, `CONTENT_VIOLATION` and `IDENTITY_VIOLATION` are the enums `HttpResource`, `ContentViolation` and `IdentityViolation`; their stable strings are the ones of the logs of the React Native app (`documentContent`, `wrongSignature`, `otherItem`...).
- `lib/features/documents/infrastructure/http_document_repository.dart` (`HttpDocumentRepositoryOptions`): `maxContentBytes` is an `int` with the default `maxDocumentBytes` in the constructor, where React Native has an optional field and defaults it when it reads it. `downloadTimeout` stays optional (the timeout of the client when absent).
- `test/features/auth/infrastructure/http_auth_session_test.dart` (the mocked client): four scenarios of `HttpAuthSession.test.ts` replace `HttpClient.request` with `jest.spyOn(...).mockResolvedValue(...)` to make the client answer a failure. `HttpClient` is a final class and a Dart test cannot replace its method, so the server sends what made the client answer so (a body of the wrong shape, a 403, a 404, a 422, a user that breaks a rule), which is the same scenario one layer lower and checks more: the client, the mapping and the sign-in together. The names are the same.

In Dart they run the client over the fixture server's dio adapter (through `createHttpWorld`), which is the same idea (the real client, the real repositories, a simulated network); the name is kept so that the two suites compare test by test.
- `test/support/infrastructure/http_adapters_world.dart` (`createHttpWorld`): the function of `httpWorld.ts` is in its own file, because `http_world.dart` holds the fixture server's support (`installFixtureServer`, `createHttpServerSide`) that the other parts of the step use without the HTTP adapters. It is synchronous (nothing in it awaits), and `HttpWorldOptions` is a class (`server` for the options of the test server, `clientTimeout` for `client.timeout`, `documents`, `storage`) where React Native passes a partial object; `HttpWorld` holds the server side as `serverSide` and forwards `clock`, `network`, `backend`, `api`, `files`, `accounts` and `load`.
- `test/features/documents/infrastructure/http_document_repository_test.dart` (the files): the test that reads the file back needs a real directory, so it gives the test server a `FileStore` over a temporary directory (`testFileStore`), as React Native's reads through `NodeFileVolume`. The cause the monitoring gets when the volume fails is `os error 5` (the number of the error), where React Native's is `EIO` (see `describeFailure`, above).
- persistence, the layer under the adapters (`lib/app/persistence/boardroom_database.dart`, `SqlDatabase.ts`): drift is the seam React Native writes by hand. `BoardroomDatabase` (the drift database over the executor of the connection `openProtectedDatabase` unlocked) replaces `SqlDatabase`, `createSqlDatabase`, `SqlConnection` and the serial queue of the statements: drift runs the statements of one executor in order, and a transaction holds the executor until it ends (the tests of `SqlDatabase.test.ts` run on `BoardroomDatabase`, and the contract suites with concurrent writers pass). drift opens the transaction with `BEGIN`, where React Native's is `BEGIN IMMEDIATE`; with one connection there is no second writer for the difference to matter. `DriftDocumentCache` keeps its own serial queue, as `SqliteDocumentCache` does.
- persistence, names (`drift_meeting_cache.dart`, `drift_document_cache.dart`, `drift_vote_outbox.dart`): `SqliteMeetingCache`, `SqliteDocumentCache` and `SqliteVoteOutbox` are `DriftMeetingCache`, `DriftDocumentCache` and `DriftVoteOutbox`, as the brief names them, since the engine is no longer reached through SQL text of their own; their tests keep the scenario names under the new class name (`createSqlDatabase` is `BoardroomDatabase`, `ExpoSqliteOpener` is `Sqlite3Opener`). `SqliteMeetingCacheOptions` and `SqliteVoteOutboxOptions` (three fields) are named parameters of the constructor, `SqliteDocumentCacheOptions` (four fields) is the class `DriftDocumentCacheOptions` (`docs/porting.md`, section 6).
- persistence, reads and writes (`drift_*.dart`): a write goes through the tables of drift (`insertOrReplace`, `update`, `delete`, in a `transaction` where React Native has one), a read through `customSelect` and the raw row (`QueryRow.data`) that is checked column by column. The typed read of drift casts each column (`as int`), so a row that was altered (a text in a number column, `1.5` in `attempts`) would make the read throw, where the outbox must quarantine the row and the caches must treat it as a miss, as `zod` does in React Native. The statements of the reads are written from the names of `schema.dart`, as in React Native.
- persistence, tables (`tables.dart`): `drift_dev` reads `.named(...)` and `tableName` as literals and ignores anything else (a warning at each use), so the tables do not repeat the names of `schema.dart`: drift derives them from the Dart names (`cursorKey` is `cursor_key`, `MeetingPages` is `meeting_pages`). `tables_test.dart` checks that the derived names are the ones of `schema.dart`, and that the columns, the types, the nullability and the primary keys are the ones the migrations create. The constraints (`CHECK`, `UNIQUE`, `AUTOINCREMENT`) are the migrations' alone, because the file is never created from the declarations of drift.
- persistence, migrations (`migrate.dart`, `migrate.ts`): drift runs the migrations when it opens the file (`MigrationStrategy`: `onCreate` from version 0, `onUpgrade` otherwise), each one in its own transaction with `PRAGMA user_version = N`, as React Native does, so a migration that fails leaves the file at the version before it (tested). There is no `runMigrations` and no `MigrationOutcome` (`{version, applied}`): the tests look at `user_version`. The failure is thrown as `MigrationFailure` (kinds `invalidMigrations`, `databaseIsNewer`, `migrationFailed`, with the version and a cause that is a result code) for `openProtectedDatabase` to turn into `DatabaseFailureReason.migration` or `databaseIsNewer`, which is what React Native maps. `VersionUnreadable` has no counterpart: drift reads the version itself, and a failure to read it is a failure to open.
- persistence, an empty list of migrations (`migrate_test.dart`): React Native does nothing and leaves the database at version 0; drift refuses a schema with no version (`schemaVersion` must be positive), so an empty list is `invalidMigrations`, like a gap or a list that does not start at 1, before the file is touched. A version that is not whole cannot be written (`Migration.version` is an `int`).
- persistence, the failures of drift (`guarded.dart`): drift wraps a failure of the engine in two cases, a statement it explains (`DriftWrappedException`) and a transaction whose rollback fails after the work failed (`CouldNotRollBackException`). `engineFailureOf` takes the failure underneath before `describeFailure`, so the cause of the storage error stays `sqlite error N`, and a rollback that fails too reports the failure of the work, which React Native does by hand ("the original failure is the one to report"). `shared/attempt.dart` is untouched.
- persistence, the unlock (`unlock_database.dart`): the statements are `PRAGMA cipher = 'sqlcipher'`, `PRAGMA key = "x'<key>'"`, `PRAGMA cipher` (SQLite3MultipleCiphers answers the cipher; plain SQLite answers nothing) and the read of `sqlite_master`, where React Native sends the key, `PRAGMA cipher_version` and the read. The decision is the same: no answer is `encryptionUnavailable`, "file is not a database" (message or result code 26) is `keyRejected`, anything else is `failed`, and a connection that does not unlock is closed.
- persistence, the tests of the encryption (`protected_database_test.dart`, `unlock_database_test.dart`, `watched_opener.dart`): React Native had no cipher on the machine that runs the tests and simulated the answers of SQLCipher (`SimulatedCipherOpener`); here the files are encrypted for real, so the key of a wrong file is rejected by the engine and a corrupted file is a file overwritten with other bytes. Two consequences: a key binds a file only when something is written to it (an empty file opens with any key), so the tests write a table before they open the file again; and the cipher that is "taken away" (`encryptionUnavailable`) is the wrapper hiding the answer of `PRAGMA cipher`, since SQLite3MultipleCiphers cannot be made plain. The tests that open the database from the protected path need the native library of `sqlite3` (the build hook), as `encrypted_sqlite_test.dart` does.
- persistence, a database in memory (`test_database.dart`): SQLite3MultipleCiphers refuses a key on a database in memory, so the tests of the caches and of the outbox that do not go through `openProtectedDatabase` open a plain database (in memory, or in a file of a temporary directory when the suite must close it and open it again); the encryption of the file is tested by the protected database and the encrypted-file tests. The contract suites run on a file (every group) and on a database in memory (the `reopen` groups are skipped), under the names `DriftMeetingCache` and `DriftMeetingCache in memory` (the same for the document cache and the outbox).
- persistence, the random key (`random_key.dart`): `secureRandomBytes` is `Random.secure()`, the secure generator of the operating system through the Dart runtime, which throws instead of falling back on a weaker source, as `expo-crypto` does (which of the system calls it makes is the runtime's choice, and has been run on no device here). `RandomBytes` answers a `Uint8List`, so the React Native scenarios where the generator answers a string or an array of numbers cannot be written; the length (32 bytes) and the all-zero check stay.
- persistence, the connection set up (`protected_database.dart`): when `PRAGMA secure_delete = ON` fails, the connection is closed before the failure is reported (`open`); React Native leaves it open. A list of migrations that is not 1, 2, 3, ... is refused before drift is given the connection, with the connection closed.
- persistence, the thread of the database (`sqlite3_opener.dart`): `NativeDatabase.opened` runs SQLite on the isolate that opened it, which is the one of the interface, where `expo-sqlite` runs its calls off the JavaScript thread. The statements are small and local; a database in a background isolate (`NativeDatabase.createInBackground`) would need the unlock to run inside that isolate, and is left for a measurement to ask for.
- persistence, the backups (`sqlite3_opener.dart`): the files are in `getApplicationSupportDirectory`, the private storage of the app on both platforms; Android's backups are off (`android:allowBackup="false"`). On iOS the directory is part of the iCloud backup (the folder is not marked `NSURLIsExcludedFromBackupKey`, which needs native code), as the `SQLite` folder of `expo-sqlite` is in React Native. The port contract says "excluded from backups": it holds in the sense that matters, because the file is encrypted with a key that never leaves the device (the keychain item is `unlocked_this_device`), so a restored file is read as a lost key and set aside (`keyLost`).
- persistence, the payloads (`stored_meeting.dart`, `stored_document.dart`): the stored classes are read with `json_serializable` in checked mode, as the wire classes are, so a payload that breaks the shape reports the first flaw only (React Native's `zod` lists up to ten, see above), and the JSON is written in the order of the fields of the class; the tests that hold the rows "as the first version wrote them" pin the exact text, as React Native's do. `position` and `pageCount` are `num`, to let the factories of the domain answer `notAnInteger` for `1.5`, as `z.number()` lets them.
